# Task dispatch — a task may run other tasks

> Slug: `dispatch` · Status: implemented on `cez/c57e477b` · Default on; `CEZ_DISPATCH=0` turns it off → `capabilities.dispatch`
> Supersedes: `2026-09-08-units-hierarchy.md`, `2026-09-09-units-v2.md`, `2026-09-09-units-improvements-plan.md`
> (the missions/units feature was removed after the research in `units-research/00-verdict.md`).

## TLDR

There are no ranks and no missions. Any running task may dispatch other cezar tasks through a CLI,
`cez task create`, and a dispatched task reports back with `cez task report`. Each child runs in
its own worktree forked off the parent's committed branch, autonomously, with a budget carved out
of the parent's that returns unspent when the child settles. The child's report is delivered into
the parent's session; the parent validates, merges into its own branch, and never merges into the
base branch. A child dispatched with `--kind review` judges another task's branch and answers with
a verdict. Tasks communicate through a tree directory on disk; the engine is the signal.

The cockpit shows children nested under their parent in the task lists and the sidebar. One
default prompt template, "Review open PRs", is the worked example of a dispatching task. Nothing
else was added.

## Why this shape

The research (`units-research/`) found: hierarchy helps only on genuinely independent, parallel
work and hurts on coupled work; cheap workers pay only when verification is not cheap; a reviewer
reduces bias but cannot verify a completion claim; and unattended runs beyond ~1–2 hours of human
work mostly fail. So the primitive is a flat, per-task decision to dispatch, guarded by a prompt
that says when not to, with hard caps in the engine, and the review kind as the one validated
second-agent pattern.

## Contract (`packages/contract/src/dispatch.ts`)

- `runRecordSchema.dispatch?: { rootRunId, parentRunId?, kind?, reviewOf?, budgetUsd?, report?, pendingReports?, inboxSeenAt?, pendingAsk?, overBudget? }`.
- `POST /api/v1/p/:projectId/runs/:id/dispatch` body `dispatchInputSchema` (strict: title?, objective, kind?, review_of?, scope?, writeTarget?, writePaths?, allowed_tools?, max_cost?, success_criteria?, required_evidence?, retry_limit?, runner?, model?) → `201 {id, branch?}` or `409 {error}`.
- `POST …/runs/:id/report` body `dispatchReportSchema` (status, result, evidence, confidence?, side_effects, errors, recommended_next_action?, verdict?, suggestions) → `{ok: true}` or `404`.
- `capabilities.dispatch` in `/health`.

## Engine (`packages/cezar/src/workflows/run.ts`, `src/dispatch/*`)

`dispatch()` (cap, budget carve, envelope, order/notes/brief/ledger, `dispatchedThisTurn`),
`recordReport()`, `handleDispatchTurn()` (budget brake, own-inbox delivery, inbox wake),
`reportSettledChildToParent()` (persist, report file, suggestions to the root's inbox, delivery
ladder), `cancelDescendants()`, `recordAsk()`/`clearPendingAsk()`; `tryAutonomousNudge` never fires
past a dispatch, a budget halt or a dispatched run's own question. `agentEnv` adds `CEZ_API_URL`,
`CEZ_PROJECT_ID`, `CEZ_BIN` and `CEZ_TREE_DIR` — behind the same `dispatchReachable()` gate the prompt
uses, so an agent is never told about a CLI it was given no address for, nor given an address it
was not told about. The prompt tells every task to write its notes and inbox messages under
`CEZ_TREE_DIR`, so the claude runner (`buildClaudeArgs`) adds `Edit(//<tree dir>/**)` to a grant
without `Write` (a `--tools` order, a narrow workflow step): claude applies that rule to `Write`,
and the rest of the filesystem stays as the grant left it.

## Prompt (`packages/cezar/src/dispatch/prompts.ts`)

One `DISPATCH_PROMPT` in every task while the flag is on: when to dispatch (independent work) and
when not to (coupled work), the CLI, disjoint scopes, commit before dispatching, the 4-child cap,
monitoring park, reports as claims, merge into own branch only, review kind, the tree directory,
the Guard. `REVIEW_PROMPT` for `--kind review`: falsify a checklist, artefacts before narrative,
verdict required.

## Not done (deliberately)

Engine-executed verification commands, model escalation on failure, a live per-unit spend brake,
mission-scoped concurrency, missions routes and cockpit pages, ranks, ladders, per-repo role
prompt overrides. See `units-research/00-verdict.md` for the ranked follow-ups.

## Write ownership and protected configuration (2026-09-22)

`writeTarget: {repository, number}` is explicit metadata on the run and dispatch input. GitHub
poll launches derive it from `GithubCandidate.repo/number`. The manual composer POST requires a target
for PR fix/autopilot/review skills and workflows: an explicit leading PR number resolves against the
GitHub remote, or a leading GitHub PR URL supplies the repository. Missing targets fail closed;
incidental references in prose and generated titles never grant ownership.
Within a project's RunManager, checking unfinished records and reserving the target are synchronous.
Queued and parked owners count. Persisted records preserve ownership across manager recovery.
Children inherit their parent's declared target unless their order explicitly names another.
A parent may delegate down its ancestor chain, with one sibling writer at a time; it coordinates
while the child writes by contract; the engine does not suspend its shell writes. Parallel variants cannot share a target. Independent targets remain parallel.
This is an orchestration guard, not a sandbox for arbitrary shell commands or a cross-host GitHub lock.

Terminal parents keep child reports pending, without an automatic continuation. Manual Continue
rechecks and reserves ownership before asynchronous startup. Targeted runs do not automatically
resume after usage limits once their terminal state released ownership. Existing in-place working-tree
leases still govern files; they are a separate mechanism and are not duplicated here.

`writePaths` declares repository-relative intended writes. Claude preflight refuses declared
`.claude/**` writes before spawning and identifies the current worktree as requiring supervision.
No agent-supplied approval boolean, alternate tool, or global permission bypass grants access.
The operator uses the existing interactive CLI handoff in that worktree and approves only its
required paths. Undeclared paths still meet the backend's own permission boundary: the first
`permission_denials` result ends the session with an error and emits no turn-end/nudge.
A retry requires operator intervention; the task does not silently switch backends or permissions.

Amended 2026-09-25: a denied turn the agent finished anyway settles on its own marker instead.
When the denied turn's text ends with `CEZ:DONE` or a valid `CEZ:ASK`, the runner records the
denied calls in a note and ends the turn with `turn-end { permissionDenied: true }`: `CEZ:DONE`
closes the session as usual, `CEZ:ASK` parks at `waiting` with its card. A denied turn is never
continued without a human: no autonomous nudge and no monitoring park, so the monitoring wake
timer cannot re-prompt it either. A denied turn ending with `CEZ:MONITORING` or with no marker
still fails as above. Evidence: of 12 denied runs on 2026-09-24/25, 4 had ended with `CEZ:DONE`
and 1 with `CEZ:ASK`, and all 12 were recorded as failures.
