# A host reconciler starts unattended work

Status: proposed

Unattended work in the design4pro pipeline starts from three places that do not know about each other. Cezar automations fire on a GitHub poll or a schedule and launch one task per event (ADR 0005, ADR 0008). Each application repo's cron runs a `housekeeping.sh` at fixed hours. A person starts everything else from the cockpit. All three are edge-triggered, and an edge that is missed is work that nobody starts: a launch that failed with `launch-error` stays a receipt and the occurrence is spent; a run that died on an OAuth refresh or a 30-minute wall clock stays `failed` until a person notices it; a ticket whose blocker closed has no event that says it became ready. None of the three counts slots across the projects that share one `maxParallel`, and none stops when a provider's usage window is shut, so the work that does start joins a queue of failures. Between 2026-09-24 and 2026-10-01 the failures were found by reading the cockpit by hand.

The decision is one small host process, the **Reconciler**, that is level-triggered where the rest are edge-triggered. `host/reconciler/reconcile.mjs` is a Node script that cron runs every ten minutes under `flock`. Each tick reads the cockpit (`GET /runs` of every registered project, the workspace's `maxParallel`), each managed repository (`node .ai/scripts/backlog-status.mjs --plan`, the automation receipts) and GitHub, decides with one pure function of that snapshot, and does what it decided. It remembers one small file, and a tick that finds nothing to do ends in a second.

1. **It starts a task only when the whole workspace has a slot.** Capacity is `maxParallel` minus the runs that hold or wait for a slot in every registered project, counted the way the engine's `busySlots` counts them, so a repo cezar was not told to manage still uses up the budget. A project may have two runs that hold a slot and one run per kind. A target an active run names, or one whose run failed or was cancelled in the last 48 hours, is not started again, and neither is a target the same workflow finished as `done` in the last 6 hours.
2. **It stops when the account has no window.** While any run is parked on a usage limit the tick launches and repairs nothing; the engine resumes the parked run itself.
3. **It repairs a failed unattended run twice, then hands it to a person.** A run with a session is continued with a text that names the failed step; a run without one is relaunched; the second attempt asks for an independent root-cause pass. After that it posts a `🤖 HUMAN-ONLY:` comment and sets `blocked` on the issue the task names, the same hold ADR 0008 defines. An error that repeating cannot fix is never retried.
4. **It asks the repository what is next, and does not decide that itself.** What is ready, in what order and with which workflow is `backlog-status.mjs --plan` in the application repo (ADR 0008's one implementation of "ready"). A repo that does not print a plan launches nothing, and the reconciler still repairs and reports for it.
5. **It reports once a day.** The first tick at or after 07:00 Europe/Warsaw replaces the body of one open issue, `Pipeline status`, with what waits for a person and what the pipeline did. One issue, edited in place, never a comment thread.
6. **It keeps open pull requests moving.** A merge leaves every other open pull request behind, CI turns a head red or green, a person approves QA by label, and nothing fires on any of that: the PR automations listen for `opened` and `reviewed`. A tick merges the base into a pull request that is behind and mergeable through GitHub's `update-branch` (no run, no slot), and starts `pr-autopilot`, ahead of the plan, on one that is green and waits on no person, one that conflicts, and one whose checks failed. Unlike decision 4 this is the reconciler's own judgement, because it is a fact of GitHub, not of a repository's backlog, and it is the same in every repo. It leaves drafts, forks and bots alone, and never moves a branch a run is working on or a person labelled `do-not-merge`, `blocked` or `in-progress`.

The engine does not change. Everything the reconciler needs is already a route (`POST /runs`, `POST /runs/:id/continue`, `POST /automation-log/:id/retry`), a `git` call or a `gh api` REST call (the host's `gh` 2.46 has no `gh issue edit`), which is also why it can live in this fork's `host/` directory (ADR 0007) and survive an upstream release without a merge. It never merges and never closes an issue; its one write to a pull request is the base merged into the branch.

## Considered Options

- **Put the supervisor in the engine:** rejected by the owner (2026-10-02). It is the most direct place to count slots, but every line there is a line to carry across each upstream release, and the failure modes it covers are properties of this host's accounts and repos, not of cezar.
- **More automations, one per gap** (a retry automation, a repair automation, a digest automation): rejected. An automation launches one task per event and writes a receipt before it does, which is exactly the edge-triggered shape that strands work. A repair automation also has no way to see that the workspace is full.
- **A long-lived daemon with its own loop:** rejected. It adds a process to supervise and a place for state to diverge from the cockpit, and cezar's own rule is that a mechanism should be invisible: no process to manage, no port to remember. A cron tick that forgets everything between runs cannot drift.
- **An agent that supervises the others:** rejected. Its decisions are the part that must be reproducible and cheap, and a model call per tick spends the same account budget the work it supervises needs.

## Consequences

- One more thing runs on the host. Its whole footprint is one cron line and `~/.cache/cez/reconcile-state.json`; removing the line stops it, and deleting the file only gives a failed run its two repairs again.
- A person's brakes stay in place: the `authors` gate and the `blocked` / `do-not-merge` holds in `backlog-status.mjs`, the security specialist's verdict on `risk-high` work, `maxParallel`, and each repo's own merge rule (the reconciler starts runs; whether a PR merges is decided by that repo's PR autopilot and its risk labels). The reconciler adds a limit of two slot-holding runs per project, 20 seconds between starts, and `--max-launch`.
- A repo adopts it by adding `--plan` to its `backlog-status.mjs` and a `--project` to the cron line. Until then it only gets repair, retried receipts and the digest. When a repo adopts it, the repo's own scheduled "implement the next ready issue" automation (ADR 0008, decision 2) becomes a second starter of the same work: it has to be disabled in the same change, or two runs can take one issue.
- The digest and the escalation write to GitHub as the host's `gh` login, so they appear under that account. `GH_CONFIG_DIR` on the cron line selects another login.
- The usage-limit pause is global by design: one parked account stops every project's unattended work, including a project whose runs use another account. That is the cheap failure; counting a window per account would need the agent-profile resolution the engine owns.
